# Phase 1 Data Model: Warehouse File Type and Packing Item Type Management

**Feature**: 002-warehouse-file-type
**Date**: 2026-08-03

---

## Entity: MovingFile (modified — new category value)

No structural schema change. The `category` field is a plain `String` (no Prisma
enum); adding `WAREHOUSE` requires no migration.

### New category value

| Category | Prefix | Auto-numbering example | Created by |
|----------|--------|----------------------|------------|
| `WAREHOUSE` | `B-` | `B-0001` | Staff manually via web app |

The file number is generated by extending the existing `CATEGORY_PREFIX` map:

```js
// backend/routes/movingFiles.js
const CATEGORY_PREFIX = { EXPORT: "E", IMPORT: "DF", LOCAL: "M", WAREHOUSE: "B" }
```

### Lifecycle

- Status values: `OPEN` → `CLOSED` (same as LOCAL; no intermediate statuses
  required in this iteration).
- Not auto-created from Jobs (unlike EXPORT/LOCAL).
- Can have `Attachment` records (same Blob storage path as other file types).

## Entity: Job (modified — new type value and auto-creation rule)

No structural schema change. `type` is a plain `String`.

### New type value

| Type | Created by | Linked file | Job number |
|------|-----------|-------------|------------|
| `WAREHOUSE` | Auto-created when a Warehouse File is saved | `movingFileId` → the Warehouse File | Same as the file's `B-XXXX` number (mirrors EXPORT pattern) |

### Auto-creation field mapping

When a Warehouse File is created, the WAREHOUSE Job is created with:

| Job field | Source |
|-----------|--------|
| `jobNumber` | Same as `fileNumber` (e.g. `B-0001`) |
| `type` | `"WAREHOUSE"` |
| `status` | `"SURVEY"` (default) |
| `clientId` | From the Warehouse File's `clientId` |
| `corporateClientId` | From the Warehouse File's `corporateClientId` |
| `movingFileId` | The new Warehouse File's `id` |
| `coordinatorId` | From the Warehouse File's `coordinatorId` (if set) |
| `serviceDate` | From the Warehouse File's `fechaEntrega` or `eta` (if set) |
| `language` | `"EN"` (default) |

### Schedule entry

`syncJobScheduleEntries(job, req)` is called fire-and-forget after job creation.
The WAREHOUSE task type maps to `'ALMACENAJE'` (new entry in the taskType map in
`scheduleSync.js`). If no service date is set, no schedule entry is created
(existing behavior).

## Entity: PackingItemType (new)

| Field | Prisma type | Constraints | Notes |
|-------|-------------|-------------|-------|
| `id` | `String` `@id @default(cuid())` | unique | cuid primary key |
| `nameEs` | `String` | required, non-empty | Item type label in Spanish (for ES PDFs and UI) |
| `nameEn` | `String` | required, non-empty | Item type label in English (for EN PDFs and UI) |
| `active` | `Boolean` `@default(true)` | required | `false` = soft-deactivated |
| `createdAt` | `DateTime` `@default(now())` | auto | |
| `updatedAt` | `DateTime` `@updatedAt` | auto | |

### Prisma definition (to add in `schema.prisma`)

```prisma
model PackingItemType {
  id        String   @id @default(cuid())
  nameEs    String
  nameEn    String
  active    Boolean  @default(true)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

### Validation rules

- `nameEs`: required, non-empty string. Label shown in Spanish-language packing lists and PDFs.
- `nameEn`: required, non-empty string. Label shown in English-language packing lists and PDFs.
- No uniqueness constraint enforced at DB level (admin is responsible; a UI warning is sufficient).
- `active`: only set to `false` via the deactivate endpoint; never hard-deleted.

### Relationships

None. `PackingItemType` is a standalone catalog table in this iteration. The
mobile app will reference item type IDs and names in its local SQLite store, but
no foreign key relation exists in this web application.

### State transitions

```
active: true  ──(deactivate)──►  active: false
              ◄──(reactivate)──  (future; out of scope for this iteration)
```
