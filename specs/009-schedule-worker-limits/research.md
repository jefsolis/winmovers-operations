# Research: Schedule Worker Capacity Limits

## Decision: Capacity storage — singleton settings row vs. hardcoded config

- **Decision**: Add a `ScheduleSetting` Prisma model with a single row (fixed `id`, e.g. `"default"`) holding `dailyWorkerCapacity Int @default(30)`. Read/upsert via `getPrisma().scheduleSetting.upsert(...)`.
- **Rationale**: The spec requires the value to be user-configurable at runtime and to persist. A DB row (vs. `.env`/config file) fits the existing pattern of admin-configurable values in this app (e.g., dashboard layout stored in `StaffMember.dashboardLayout`) and needs no deploy to change. A singleton row (rather than a history table) matches the spec's Assumption that historical capacity values do not need to be versioned.
- **Alternatives considered**: Per-day capacity overrides table — rejected as out of scope (Assumptions state a single company-wide value for this iteration); environment variable — rejected because it requires a deploy/restart to change and doesn't satisfy "configurable... inside the schedule screen".

## Decision: Where capacity is enforced

- **Decision**: Centralize capacity-check logic in a new backend helper, e.g. `backend/services/scheduleCapacity.js`, exposing functions like `getRemainingCapacity(dateRange)`, `checkCapacityForSpan(startDate, days, workersRequired)`, and `findClosestAvailableSpan(...)`. Both `routes/schedule.js` (manual scheduling) and `services/scheduleSync.js` (automatic scheduling from job dates) call this shared helper.
- **Rationale**: Constitution Principle VII (centralize normalization/permission logic in explicit helpers rather than duplicating). Both scheduling paths (manual UI entries and job-date-driven auto-sync) must apply identical capacity rules per spec FR-022/FR-023 (parity requirement).
- **Alternatives considered**: Duplicating the check inline in both `schedule.js` and `scheduleSync.js` — rejected, violates the "centralize... in explicit helpers" rule and risks the two paths drifting out of sync.

## Decision: Modeling "needs attention" / override

- **Decision**: Add two columns to `ScheduleEntry`: `needsAttention Boolean @default(false)` and `overrideReason String? @db.Text`. A job occupies N consecutive `ScheduleEntry`-covered days (via `startDate`/`endDate`, already supported by the model); the flag and reason are stored on the schedule entry representing the job's occupied span (the existing auto-generated entry, or the manual entry the user created).
- **Rationale**: `ScheduleEntry` already models a date span (`startDate`/`endDate`) and is the object rendered in the Schedule UI, so this is the natural place for the flag/reason to live and be visible per FR-012/FR-013. Reuses existing fields (`isAutoGenerated`, `rangeManuallyAdjusted`) alongside the new ones without restructuring the model.
- **Alternatives considered**: Storing override reason on `Job` instead of `ScheduleEntry` — rejected because a job could theoretically have its schedule entry deleted/recreated, and the reason is scoped to "this scheduling decision", which is entry-level; also multiple schedule entries could exist per job in edge cases (manual + auto), so entry-level is more precise.

## Decision: Scheduling Manager permission

- **Decision**: Add `canManageSchedule Boolean @default(false)` to `StaffMember`, following the exact existing pattern of `canAccessSchedule`. `ADMIN` role continues to bypass permission flags (as it already does for `canAccessSchedule` in `requireScheduleAccess`). A new `requireScheduleManager` middleware in `schedule.js` checks `staff.canManageSchedule || staff.role === 'ADMIN'`.
- **Rationale**: Matches Constitution Principle III (role-based access via existing flag pattern) and avoids introducing a parallel role system. `ADMIN` bypass is consistent with how `requireScheduleAccess` already treats `ADMIN`/`BODEGA`.
- **Alternatives considered**: A generic multi-role string enum replacing boolean flags — rejected as a much larger refactor of `StaffMember`, out of proportion to this feature (Principle VII, incremental low-risk change).

## Decision: "Closest available date" search algorithm

- **Decision**: Given a requested start date and job duration (days), search outward: check day offsets 0, +1, -1, +2, -2, ... up to a bounded window (e.g., 60 days) for the first offset where every day in the resulting span has `remainingCapacity >= workersRequired`. Return up to 3 suggestions (closest forward, closest backward, and next-closest) or however many are found within the window.
- **Rationale**: Spec explicitly says "searching forward from, then backward from, the requested date" and requires a bounded, non-exhaustive search (Assumptions). Symmetric outward search naturally yields "closest" per FR-009.
- **Alternatives considered**: Forward-only search — rejected, spec explicitly calls for both directions; unbounded search — rejected per Assumptions (bounded window, inform user if nothing found).

## Decision: Auto-scheduling integration point

- **Decision**: Extend `scheduleSync.js`'s `_syncEntry`/`syncJobScheduleEntries` to: (1) require `job.workersRequired` before creating an entry (else skip creation and surface a warning via the job API response), (2) compute the job's occupied span from `job.serviceDate/moveDate` + `job.daysToComplete`, (3) call the shared capacity helper before creating/updating the entry, (4) on insufficient capacity without override, skip auto-creation and return a structured "capacity" warning to the caller (`routes/jobs.js`) rather than silently creating an overbooked entry.
- **Rationale**: Preserves existing auto-generation behavior (Constitution VI) while layering the new rule in; keeps the "fire-and-forget" sync function but returns enough info for `jobs.js` to warn the user, matching FR-005/FR-009.
- **Alternatives considered**: Moving all scheduling logic into `jobs.js` directly — rejected, duplicates logic already centralized in `scheduleSync.js` and used by both job create and update flows.

## Decision: Frontend surfaces

- **Decision**: Capacity control, override dialog, suggested-dates prompt, needs-attention badge, and manager resolution tools all live in `frontend/src/pages/Schedule/`. Job form fields (`workersRequired`, `daysToComplete`) live in `frontend/src/pages/Jobs/`. Dashboard card follows the existing `DASHBOARD_CARDS` registry pattern in `dashboardCards.js` + a new section in `Dashboard.jsx`.
- **Rationale**: Matches existing page/module boundaries; no new top-level frontend module needed.
- **Alternatives considered**: A dedicated "Capacity" settings page — rejected, spec explicitly says configuration lives "inside the schedule screen".
